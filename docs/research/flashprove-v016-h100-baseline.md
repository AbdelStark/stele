- **Epic:** `AbdelStark/stele#453` · **Child issue:** `AbdelStark/stele#454` · **Lane:** B (`E17-01`..`E17-04`)
- **Upstream pinned commit:** `anthropics/FlashProve` `v0.16.0` (`9e2bdd8ff5bf9c62f18263d7dac189b0400b260c`)

This document pins the external FlashProve `v0.16.0` single-H100 baseline on full-scale Llama 4 Maverick (400B, 128 routed experts + 1 shared expert, 48 layers), documents the arithmetic comparison against Stele CQIS (RFC-0004, RFC-0017), publishes the 120-window expected-token oracle, exposes the measured discrepancy against the upstream published figures, and predeclares the paired statistical protocol for the head-to-head reproduction in issue `#464` (RFC-0018 §1 rule 3). All memory sizes in `GB` and `MB` are decimal (`1 GB = 10^9 B`, `1 MB = 10^6 B`, converting GNU `time -v` KiB via `kib * 1024 / 10^9`), matching `bench/scoreboard.md` and FlashProve's `guide/performance.md`; GPU memory from `nvidia-smi` is reported in binary `MiB` (`2^20 B`).

### Unrecoverable upstream settings

Per `anthropics/FlashProve` `guide/performance.md` (rows `RES-6`, `RES-18`, `T49`), four inputs of the upstream published runs are absent from the public repository and cannot be recovered verbatim:

1. **Prompt corpus:** Upstream's 96 timed prompt windows are not published. Following `guide/performance.md` §"Reproduce the numbers", this baseline freezes the deterministic 120-window expansion of `calibration_set.npy` generated by `driver/measure_rate.py` (exact per-window request SHA-256 digests in [`flashprove-v016-maverick-h100.json`](../../bench/baselines/flashprove-v016-maverick-h100.json)).

3. **Two parameter lines:** Upstream's timed services used each commitment's own parameter file where 2 of 152 model lines differed from the repository file without a published checksum; our runs use the exact Route-4 fitted configuration whose digests match `examples/maverick/expected.txt`.
4. **Host SKU & co-tenancy:** Upstream's 96-CPU 8-GPU shared host SKU, interconnect generation, memory channels, and CPU reservation state are not published (upstream notes up to 9% cross-machine and 6.3% session-to-session variation).

Per RFC-0018 §1 rule 3, cross-system numbers must state both arithmetic specifications explicitly:

| Operation / property | FlashProve `v0.16.0` (`docs/model.md`) | Stele CQIS (`RFC-0004`, `RFC-0017`) |
|---|---|---|
| Architecture shape | Llama 4 Maverick: `L = 48`, `d = 5120`, `H = 40`, `G = 8`, `dh = 128`, `f = 16384` (even dense layers), `fe = 8192` + `NE = 128` top-1 routed + 1 shared expert (odd MoE layers), `V = 202048`, `T = 1024`, RoPE omitted where `l mod 4 = 3` (`rp = 0`) | Same Maverick dimensions and layer alternation targeted at L5 (`RFC-0017` row 4, task `E22-07`) |
| Weight precision | Integer matrices in `-4096..4095` (13-bit signed from Q4_K_XL conversion; norm gains folded into matrices); embedding `Emb` signed 32-bit (`|x| < 2^30`) | Packed quantized weights (int4/int8) with static per-tensor/group scales and explicit int16 RMSNorm gains (`RFC-0004`) |
| Activation / stream range | Activations `a, m, v, aF, Q, K` clamped to `[-2047, 2047]` (12-bit signed); residual stream wide 5-limb (`xl = 5`); up projection limited to 16 bits (`ut = 1`) | Static bit-width checked residual stream (`int16` or wide stream `RFC-0004 A14`), static bounds checked in `Relation::validate` (INV-5) |
| Requantization | `rq(a, k) = floor((a + 2^(k-1)) / 2^k)` (round-to-nearest ties up) with static per-layer power-of-two shifts in `KL.bin` | Fixed-point shift/round with exact remainder/carry decomposition checked over `M31` (INV-5) |
| RMSNorm | Exact integer `isqrt`, per-norm exponents `(M1, K1, M2, K2, MF, KF)`, regularizers `eps1, eps2, epsF` | Exact integer `rsqrt` lookup table (`RFC-0004` §5.3, A2) with explicit gain multiplication |
| RoPE | Float64-generated integer tables `C, S = rha(2^12 * cos/sin(t * 500000^(-2i/dh)))`, `rp = 0` on `l mod 4 = 3` | Precomputed public RoPE tables with pair-permutation matmul (`RFC-0026 A1`) |
| Nonlinear tables | Softmax `EX[u] = rne(2^12 * exp(-u/256))`; SiLU `Ts[c] = clamp(rha(64*s), 4095)` (`c in -32768..32767`); Sigmoid `Sig[c] = 16*rha(4096/(1+exp(-c/256)))` | Exact CQIS lookup tables (`exp`, `silu`, `rsqrt`, `sigmoid`) verified by LogUp-GKR (`RFC-0008`) |
| MoE routing | Router `Wr` (`d x 128`), sigmoid gate + top-1 argmax (`argmax` = least index), shared expert + 1 routed expert per token | Exact integer router + top-k/top-1 argmax oracle (`RFC-0017` row 4, task `E22-07`) |
| Proof field & argument | Goldilocks cubic extension, interleaved Reed-Solomon (~0.10 rate) + BLAKE2b Merkle, masked sumchecks, grand-product lookups, approximate 128-projection range checks | `M31` / `QM31` (and `OM31` where required), Circle-RS / interleaved-code PCS, sumcheck + LogUp-GKR + exact range lookups |

### Discrepancy exposure and root-cause explanation

Our single-H100 SXM5 reproduction runs **+29.95% faster at batch 24** (`144.54` vs `111.23 tok/s`, `170.023 s` vs `220.7–225.9 s` per batch) and **+168.8% faster at batch 1** (`46.80` vs `17.41 tok/s`, `21.877 s` vs `58.796 s` per request), while proof sizes (`18.78` vs `18.78 MB`), commitment sizes (`6.23` vs `6.24 MB` `ivk`, `2.15` vs `2.15 GB` `isk`), `cp_commit` RSS (`297.60–297.65` vs `299.6 GB`), `cp_verify` single-thread latency (`18.40` vs `~21 s`), and `cp_verify` peak RSS (`3.50–3.53` vs `3.53 GB`) match upstream closely:

1. **Dedicated H100 SXM5 + PCIe Gen5 + Sapphire Rapids DDR5 NUMA bandwidth:** Our H100 SXM5 operates at `700 W` (`1980 MHz` SM, `2619 MHz` HBM3, `3.35 TB/s`) paired with 24 dedicated NUMA-local `Xeon Platinum 8480CL` cores and `2,163.64 GB` DDR5 host memory, with zero co-tenant contention. At batch 1, proving is dominated by streaming the ~232 GB model weights from host memory over PCIe to the GPU for a single request, amplifying host-DRAM/PCIe bandwidth advantages by `2.69×` compared with `1.30×` at batch 24 (where 6 requests amortize each weight pass).
2. **Host memory & page cache headroom:** `cp_prove` reaches `257.05 GB` RSS; on a constrained ~330 GB slice of a shared 96-CPU host, little OS page cache remains for the 232 GB GGUF weight files, whereas `2,163.64 GB` host RAM keeps weight shards resident after `cp_commit`. Longer startup (`115.085 s` vs `68.1–79.0 s`) reflects initial cold weight loading and pinned-memory setup on our storage/allocator configuration.
3. **Target impact for `#463` and `#464`:** Stele's L5 single-H100 target on this hardware class must beat **both** the upstream published `111.23 tok/s` **and** our same-machine reproduced **`144.54 tok/s`** at batch 24, while keeping batch-1 latency `<= 21.877 s` (and well under the `<= 30 s` epic ceiling), proof size `<= 4 MB` (vs FlashProve `18.78 MB`), and CPU verification `<= 2 s` (vs FlashProve `16.98–18.40 s`).

## 6. Preregistered head-to-head protocol for issue #464

Predeclared before Stele tuning begins (fixed sample size to prevent optional stopping):

1. **Hardware & image parity:** Both systems execute on the identical single-H100 80 GB SXM5 + 24 NUMA-local Xeon 8480CL CPU allocation, locked to the same power/clock/ECC/THP policy, GPU persistence mode ON, exclusive GPU reservation, with immutable digest-pinned (`@sha256:`) container images recorded in every ledger.
2. **Workload & statement:** Identical 120-window (`B = 24`, 5 batches) and 6-window (`B = 1`, 6 batches) `calibration_set.npy` corpus (`a2ce04bd55b1b6fa...`), 1,024 prompt tokens per request, next-token statement, masking / cross-request zero knowledge enabled on both systems, every proof verified by its ordinary CPU verifier.
3. **Fixed interleaved independent sessions:** For each batch size `B in {1, 24}`, run exactly **`n = 4` independent paired sessions** (`df = 3`, two-sided `t_{0.975, 3} = 3.182446`) in balanced interleaved order **`(AB, BA, AB, BA)`**, with a fresh prover process launch per session (one independent session = one sampling unit; no optional stopping).
4. **Rate definitions (reported separately):**
   - **Primary (steady-state prover rate, matching `driver/measure_rate.py`):** Discard batch 1 (warmup); compute `rate = (B * 1024 * (K - 1)) / (release_K - release_1)` where `K = 5` for `B = 24` and `K = 6` for `B = 1`.
   - **Cold rate (with startup):** `(B * 1024 * K) / (release_K - process_start)`.
   - **Verified end-to-end rate:** `(B * 1024 * K) / (verify_all_done - process_start)` (reported both excluding and including prover shutdown, with CPU verifier concurrency and thread count stated explicitly).
   - **Commitment setup:** Reported separately (wall time, peak host/GPU memory, verifier key size, prover state size).
5. **Decision criterion (`#464`):** On the `n = 4` paired per-session log-rate ratios `d_i = ln(rate_stele_i / rate_flashprove_i)` (`i = 1..4`), compute the exact two-sided Student-`t` 95% confidence interval `exp(mean(d) ± t_{0.975, 3} * sd(d) / sqrt(4))`. Victory requires the **95% CI lower bound `> 1.0`** at `B = 24`, batch-1 steady latency beating both `30 s` and the paired FlashProve batch-1 mean, proof size `<= 4 MB/request`, CPU verification `<= 2 s`, and 100% verifier acceptance plus all negative controls rejected.
