# STELE — the inference-native proof system

> **Stone → Stwo → Stele.** Stone made STARKs real. Stwo made the field cheap (Circle STARKs over M31).
> Stele makes the *computation* disappear from the proof: **the prover never pays for a multiply‑accumulate.**

Stele is a from‑first‑principles, treaty‑grade, zero‑knowledge proof system for **neural‑network inference**
(frontier transformers: dense, MoE, MLA, GQA, long context). It is not a general‑purpose zkVM and not a fork
of any existing prover. Its design goal is a proving cost that is **linear in the bytes the inference touches
(weights, activations, lookups) and independent of the FLOPs it performs**, executed on the same GPUs that serve
the model, with soundness that a hostile nation‑state auditor can check line by line.

| Property | Stele target (see `docs/plan.md` §3, `docs/cost-model.md`, RFC‑0018) |
|---|---|
| Per‑proof weight cost | **one streaming pass** over the (packed int4/int8) weights, regardless of layers, sequence length, batch |
| Intermediate commitments | **advice only** — one or two small integers per nonlinear value (rounding outputs, table indices), the residual stream at segment boundaries, multiplicity vectors. No arithmetic result is committed (RFC‑0028, Draft) |
| Per‑activation cost | one or two committed cells and two or three lookups (LogUp‑GKR, ≈ 10² M31 ops each) |
| Attention | `O(n²·h)` **exp lookups**; scores are never committed; probabilities are committed unless an indexed lookup leaves them virtual (RFC‑0019 Q35) |
| Field | Mersenne‑31 base, QM31 (degree‑4) challenges; no FFT over the weights per proof, one short circle FFT per committed witness row |
| Commitments | hash‑based, interleaved circle Reed–Solomon with a recursive opening (RFC‑0029, Draft); **fused opening** — the matmul sumcheck’s weight pass *is* the opening |
| Security | hash + Fiat–Shamir only, no discrete‑log or pairing assumption; `standard` ≥ 100 bits and `treaty` ≥ 128 bits per round with **no conjectural bounds** (RFC‑0030, Draft) |
| Zero‑knowledge | masked sumchecks + bounded‑query encodings (RFC‑0013 A3, Draft); weights never leave the prover |
| Roofline, Llama‑3.1‑405B, 4096+512 request | ≈ 15–20 GPU‑s (1×H100), a projection (`docs/cost-model.md` §3). The published frontier is FlashProve: 111 tok/s on a 400B mixture‑of‑experts model, one H100, batch 24 (`docs/assessment.md` §6) |

The table states design targets. What exists today is in **Status** below; how the project gets from one to
the other is the build program in [`docs/plan.md`](docs/plan.md).

The project is **agent‑native**: every piece of work is specified as an RFC with acceptance criteria, guardrails and a
negative‑control corpus; agents build it, agents review it, agents benchmark it. Read `AGENTS.md` first.

## Status

`v0.1.0` plus the development end‑to‑end path.

**Works today.** One prefill window of a Llama‑style model is proved and verified end to end on CPU under the
RFC‑0026 development profile: `stele prove-dev` / `stele verify-dev` ([how to run](docs/development-e2e.md)).
A real checkpoint (llama2.c `stories42M`, 64 tokens) proves in 474 s and verifies in 24 s with a 113 MB proof on
24 threads ([ledger](bench/ledger/e16-18-dev-stories42m.json)). The larger `stories110M` proves in 1,979 s on a
128-thread host ([ledger](bench/ledger/e16-20-dev-stories110m.json)). Proof bytes are the same on every host and
thread count measured ([scoreboard](bench/scoreboard.md)).

The `dev-zk` profile (`--zk`) proves a window in zero knowledge at the development tier. The int8 weight
codes and the norm gains are hidden behind one published model commitment, which serves up to `P` proofs.
The zero knowledge is conditional and computational, and there is no security level
([RFC‑0013 A5 admission](docs/rfcs/RFC-0013-zero-knowledge.md), [how to run](docs/development-e2e.md#dev-zk-tasks-e12-14b-e12-25-e12-27-e12-14)).
- **Not hidden:** the model's shapes and per-row quantisation scales (the public Scales file), the tokens and every
  checked greedy choice (on stories42M, all 9 at positions 23..31, not only `y`), the plan, the proof index, and
  linkability under one commitment.
- **Synthetic window:** the eight-layer window proves in 27 s with a 6.4 MB proof
  ([ledger](bench/ledger/e12-28-dev-zk-synthetic-8layer-mac.json)).
- **Real checkpoint:** llama2.c `stories42M` (profile byte 4) proves on a 16-thread, 48 GB laptop:
  - at T = 32 in 519 s, verifying in 34 s, with a 21.4 MB proof
    ([ledger](bench/ledger/e16-33-dev-zk-stories42m-t32-mac-after.json); RFC‑0013 A9);
  - at T = 64 in 923 s, verifying in 47 s, with a 25.7 MB proof and a 107 GB peak memory footprint
    ([ledger](bench/ledger/e16-33-dev-zk-stories42m-t64-mac.json)). Admission at T = 64 is RFC‑0013 A10
    (accepted, development tier). stories42M is a public
  checkpoint that shows the mechanics and costs; a real deployment must not publish hashes of its hidden weights.
  15 tampers of the real proof (every proof section and public field) are each rejected with their pinned error
  (`bench/dev_zk_tamper.py`). The privacy tests pass on stories42M at T = 32: across two proofs under one
  commitment, no masked revealed final equals its bare evaluation, and the two proofs pass a two-proof χ²
  homogeneity test (the uniformity test on masked finals alone is pending a quiet-host re-run)
  ([ledger](bench/ledger/e12-32-dev-zk-stories42m-privacy-t32-mac.json)).
- **Soundness:** `verify-dev` prints a soundness ledger (worst round `2^-95.4` on stories42M; FS unproven, PCS
  conjectural).

**Does not exist yet.** A security level (the development profile claims none), zero knowledge at a security
level, a dev-zk proof of any real model other than stories42M, a GPU prover,
the `no_std` verifier crate, a passport, a proof of Llama‑3.1‑8B.

**What is solid underneath.** Fields, transcript, Merkle, sumcheck, lookup, encoder and commitment primitives
with independent Python oracles; the CQIS integer semantics with native and NumPy executors and a fidelity
report on Llama‑3.1‑8B ([`harness/eval/REPORT.md`](harness/eval/REPORT.md)); 71 of 142 control catalogue rows done.

**Where it is going.** [`docs/assessment.md`](docs/assessment.md) is the evidence. [`docs/plan.md`](docs/plan.md)
is the build program (RFC‑0027): first Llama‑3.1‑8B through the existing engine (M1), then a protocol that
commits only advice, a succinct commitment scheme and a fast CPU engine (M2), admission to a real security
level (M3), GPU (M4), zero knowledge (M5), the frontier workloads (M6), treaty grade (M7). The task graph
(`agents/tasks/graph.yaml`, epics E17–E23) is the source of truth for dependencies and acceptance criteria.

## Bootstrap checks

Rust is pinned by `rust-toolchain.toml`. With Python 3.11+ and cargo-deny 0.20.2 installed:

```sh
bash scripts/scaffold.sh
cargo build --workspace --locked --offline
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked --offline -- -D warnings
cargo test --workspace --locked --offline
cargo deny --offline check bans
python3 -m unittest discover -s scripts/tests -v
```

`deny.toml` restricts direct crate imports, including renamed, build, and test dependencies.
The isolated mutation tests verify those restrictions. Controls and accounting now exercise
the production transcript and dense sumcheck against an independent Python corpus, including
final public evaluation obligations. Instance and virtual-tensor claim batching have both-field byte, SC/RLC and rejection
checks plus a 276-case shared Rust/Python acceptance/rejection corpus and
[both-field CPU benchmark ledgers](bench/README.md#batching-e3-02).
Merkle construction/authentication agrees with the
A3 byte vectors, and both leaf kinds have an executed rejection control.
Unimplemented protocol crates still have fail-closed
scaffold guards. These checks do not establish a complete inference proof, zero-knowledge,
or a soundness profile. See `scripts/gates/README.md` for the gate contracts.
